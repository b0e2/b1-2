# TIL — Today I Learned

오늘 배운 것을 기록하고, 태그로 모아 보고, 회고와 함께 완료로 남기는 서비스입니다.

## 기술 구성

| 영역 | 사용 | 고른 이유 |
|---|---|---|
| 화면 | React 19 + Vite | 요구 사항이 React 18 이상이고 설정이 가볍습니다 |
| 라우팅 | React Router | 상세와 수정처럼 주소에 값이 들어가는 화면을 다루기 위해서입니다 |
| 데이터 | Supabase (PostgreSQL) | 다루는 데이터가 한 종류이고 값의 범위와 조건을 테이블 제약으로 표현할 수 있습니다 |
| 배포 | Vercel | 정적 빌드 결과를 올리고 연결 정보를 따로 관리하기 쉽습니다 |
| 스타일 | 일반 CSS | 화면 꾸미기보다 구조에 시간을 쓰기 위해 도구를 늘리지 않았습니다 |

## 실행 방법

```bash
npm install
cp .env.example .env   # 아래 값을 채웁니다
npm run dev
```

| 환경변수 | 설명 |
|---|---|
| `VITE_SUPABASE_URL` | Supabase 프로젝트 주소 |
| `VITE_SUPABASE_ANON_KEY` | 브라우저에 노출해도 되는 공개 키 |

Vite 는 `VITE_` 로 시작하는 값만 브라우저 코드에 넣습니다. 이름을 다르게 쓰면 값이 비어 실행 중에 실패합니다.
비밀 키는 브라우저에 넣지 않습니다. 데이터 보호는 접근 정책이 담당합니다.

데이터베이스는 `supabase/schema.sql` 을 SQL Editor 에 실행해 만듭니다. 이후 변경은 `supabase/migrations/README.md` 를 따릅니다.

```bash
npm run build     # 배포용 빌드
npm run lint      # 정적 검사
```

## 폴더 구조

```
src/
├── pages/        라우트 하나에 화면 하나. 훅을 조합하고 상태에 따라 무엇을 그릴지 고릅니다
├── components/
│   ├── ui/           기록이 무엇인지 모릅니다. 다른 프로젝트에 그대로 옮길 수 있습니다
│   └── study-logs/   기록 객체를 압니다
├── hooks/        언제 요청할지, 그 결과를 어떤 상태로 둘지
├── lib/          이 값이 올바른가, 어떻게 보일까, 무엇을 계산할까
├── contexts/     로그인한 사용자와 테마
└── styles/       토큰 → 기본값 → 레이아웃 → 공용 → 도메인 → 화면
```

컴포넌트를 나눈 기준은 **기록을 아는가** 입니다. `ui/` 안의 것들은 `log` 가 무엇인지 모르고 값만 받아 그립니다. `study-logs/` 안의 것들은 기록 객체를 받습니다.

`hooks/` 와 `lib/` 를 나눈 기준은 **React 가 필요한가** 입니다. `lib/` 는 같은 입력에 같은 결과를 내는 함수만 두어서, 검증 규칙을 확인하려고 화면을 띄울 필요가 없습니다.

## 설계에서 정한 것들

### 목록을 화면마다 따로 부릅니다

홈, 학습 목록, 태그, 통계가 각자 `useStudyLogs()` 를 호출합니다. 하나로 합쳐 전역에 두지 않았습니다.

합치면 화면마다 갖고 있던 불러오는 중과 실패 상태가 하나가 됩니다. 통계에서 실패했을 때 목록도 함께 실패한 것처럼 보이고, 어느 화면에서 다시 시도할지도 애매해집니다. 다루는 데이터가 적어 요청이 겹치는 비용보다 상태가 섞이지 않는 이점이 큽니다.

### 검색과 필터는 요청을 만들지 않습니다

검색어와 태그와 정렬은 주소에 두고, 목록은 한 번 받아온 배열에서 걸러냅니다. 이 값들을 훅에 넘기지 않으므로 한 글자 칠 때마다 요청이 나가지 않습니다.

주소에 둔 덕분에 새로고침과 뒤로 가기가 자연스럽고, 조건이 걸린 목록을 링크로 공유할 수 있습니다. 상단 검색이 목록 화면에 조건을 넘기는 통로가 되기도 합니다.

### 검증은 세 겹입니다

입력할 때와 제출할 때는 `lib/studyLogValidation.js` 의 같은 함수를 씁니다. 그리고 테이블에도 같은 규칙을 제약으로 걸었습니다.

화면 검증은 사용자를 위한 것이고 실제 보장은 데이터베이스에 있습니다. 화면을 건너뛰고 직접 요청을 보내도 완료 상태인데 회고가 없는 기록은 저장되지 않습니다.

### 완료에는 회고가 필요합니다

기록과 회고를 함께 남기는 것이 이 서비스의 목적이라, 완료로 표시하려면 회고를 열 자 이상 받습니다. 이 규칙은 목록과 상세가 같은 함수를 쓰도록 한 곳에 두었습니다. 각자 구현하면 화면마다 조건이 갈립니다.

완료를 되돌릴 때 회고는 지우지 않습니다. 다시 완료로 표시할 때 그대로 씁니다.

### 태그는 따로 저장하지 않습니다

태그는 기록의 배열 컬럼에 들어 있고, 개수와 순위는 기록에서 계산합니다. 태그 테이블을 두면 기록을 지울 때 개수를 함께 줄여야 하고 어긋나면 맞출 방법이 없습니다. 계산하면 어긋날 수가 없습니다.

각 태그의 색은 이름을 해시해서 정합니다. 같은 태그는 언제나 같은 색이고 색을 저장하지 않습니다.

## 만들면서 막혔던 것

### 접근 정책을 켜고 비워 두면 조회가 빈 배열로 옵니다

행 수준 보안을 켜면서 정책을 만들지 않으면 오류가 아니라 빈 배열이 돌아옵니다. 데이터가 없는 것으로 오해하기 쉽습니다. 테이블을 만들 때 정책도 함께 만들도록 같은 파일에 두었습니다.

### 제약에는 하위 질의를 쓸 수 없습니다

배열의 각 원소 길이를 검사하려면 `unnest` 가 필요한데, PostgreSQL 은 제약 조건에 하위 질의를 허용하지 않습니다. 전체 길이 상한만 제약으로 두고 원소별 규칙은 화면 쪽 검증이 맡습니다.

### 정책을 먼저 지우면 그 사이 전부 실패합니다

로그인을 붙이면서 접근 정책을 바꿀 때, 예전 정책을 먼저 지우면 새 정책을 만들기 전까지 모든 요청이 막힙니다. 주인을 지정하고 확인한 뒤에 지우도록 순서를 SQL 에 적었습니다.

되돌릴 수 없는 변경이라 되돌리는 SQL 을 먼저 만들어 두었습니다.

### 가입 직후에 세션이 없을 수 있습니다

메일 확인이 켜져 있으면 가입해도 로그인 상태가 아닙니다. 바로 화면을 옮기면 로그인 화면으로 다시 튕깁니다. 가입 뒤에는 안내만 보여주고 로그인 입력으로 바꿉니다.

이 프로젝트는 시연을 위해 메일 확인을 껐습니다.

### 새로고침하면 주소를 찾지 못합니다

화면 전환을 브라우저 안에서 하므로 상세 주소를 직접 열면 서버가 그런 파일을 찾지 못합니다. `vercel.json` 에서 모든 주소를 첫 화면으로 넘기도록 했습니다.

### 빌드 도구가 바뀌면서 설정 형식이 달라졌습니다

Vite 8 은 묶음을 나누는 설정을 객체가 아니라 함수로 받습니다. 객체로 두면 빌드가 실패합니다.

## 화면

| 주소 | 하는 일 |
|---|---|
| `/` | 최근 기록과 바로가기 |
| `/logs` | 전체 목록, 검색과 태그와 정렬 |
| `/logs/new` | 새 기록 작성 |
| `/logs/:id` | 상세, 완료 전환, 삭제 |
| `/logs/:id/edit` | 수정 |
| `/tags` | 태그별 기록 수와 대표 제목 |
| `/stats` | 전체 수, 연속 일수, 월별 작성, 태그 순위 |
| `/settings` | 화면 테마, 로그아웃 |
| `/login` | 로그인과 가입 |
